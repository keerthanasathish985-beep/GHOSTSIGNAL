01 / PROBLEM & PURPOSE

What we built, and why it matters

Online information about any topic — a brand, an event, a product, an institution — is scattered across news sites, tech forums, social media, Q&A platforms, and developer communities. Investigating it manually means visiting each site, judging relevance by eye, and carrying context across browser tabs. There is no structured output and no provenance.

GHOSTSIGNAL solves this in a single query: enter any topic, get a fully sourced, timestamped, ML-classified investigation report in under 60 seconds.

The problem
  • Topic research requires 6+ separate sites manually
  • No consistent schema across sources
  • No sentiment signal without reading everything
  • No timeline — impossible to see when narratives started
  • Authenticity patterns invisible at scale
What GHOSTSIGNAL does
  • Queries 6 sources concurrently in one operation
  • Normalises all records to one unified schema
  • Attaches ML sentiment + authenticity labels per record
  • Builds a 7-day activity timeline from real timestamps
  • Generates a structured, evidence-linked report

Concurrency model

Batch 1 (HN + Bluesky) runs in a ThreadPoolExecutor(2). Batch 2 (DEV + SE + Discourse) runs in a ThreadPoolExecutor(3). GDELT runs sequentially after both batches complete to respect its 1 req/5 s rate limit. Total wall-clock time ≈ max(slowest_batch1, slowest_batch2) + GDELT.

Schema normalisation

Every source record is mapped to 17 canonical fields: id, source, content, title, url, published_at, author, likes, comments, views, predicted_label, confidence, metadata.provenance… Missing fields are null, never fabricated.

Failure isolation

Each collector's future is resolved inside its own try/except. A collector raising any exception writes to collector_errors[key] and execution continues. Status is "partial" if any source failed but records were still collected; "error" only if all sources failed.

Relevance post-filter — why it exists

Algolia (HN), DEV, and SE search APIs use token-based matching: a query like "GSSS institute of engineering and technology" returns posts containing any of those words individually. The post-filter strips generic technical vocabulary ("engineering", "technology", "institute") and requires the remaining distinctive tokens to appear as whole words (\b boundary) in the hit's text. For "amazon" this prevents "amazynk" from matching.

_distinctive_tokens("amazon") → ['amazon'] _distinctive_tokens("GSSS institute of engineering") → ['gsss'] _distinctive_tokens("artificial intelligence") → ['artificial', 'intelligence'] Relevance check (whole-word): re.search(r"\bamazon\b", "amazynk repository") → None ✗ rejected re.search(r"\bamazon\b", "amazon aws pricing") → match ✓ accepted
04 / MACHINE LEARNING — OVERVIEW

Two independent classifiers

Sentiment classifier

Classifies collected text as Positive or Negative.

Labels are rating-derived: 1–2 ★ → Negative, 4–5 ★ → Positive. 3-star reviews are excluded as ambiguous.

Training data: Amazon reviews + Google reviews (combined JSONL).

Authenticity classifier

Classifies reviewer profiles as HONEST or FAKE.

Labels are reviewer-associated: a reviewer flagged fake has that label propagated to all their reviews. This model identifies writing patterns, not individual fraud.

Training data: Amazon reviews (labelled subset only).

Algorithm: TF-IDF → Logistic Regression (sklearn Pipeline)

Both classifiers use the same two-stage sklearn Pipeline: a TF-IDF vectoriser transforms raw text into a sparse numerical matrix, then Logistic Regression makes the classification decision. Both steps are fitted end-to-end so the vectoriser's vocabulary is learned only from training data, not from test data.

Why TF-IDF?
  • Scales to tens of thousands of reviews without GPU
  • Interpretable — the highest-weight features are readable words
  • Sparse matrix: memory-efficient on large vocabularies
  • Proven baseline for short-text classification tasks
  • No pretrained model dependency — fully self-contained
Why Logistic Regression?
  • Fast to train (<30 s on the full dataset)
  • Returns calibrated predict_proba scores
  • Class-weight balancing handles skewed class distributions
  • L2 regularisation prevents overfitting on rare n-grams
  • solver=lbfgs handles multi-class natively
05 / ALGORITHM — TF-IDF

How TF-IDF works

TF-IDF (Term Frequency – Inverse Document Frequency) converts a text into a numerical vector where each dimension is a word or 2-word phrase (n-gram). Words that appear often in one document but rarely across all documents get high weight; common words like "the" get low weight.

Term Frequency (TF)

How often a term appears in the document, normalised by document length.

TF(t, d) = count(t in d) / total_terms(d) Example: "great product great price" (4 words) TF("great", d) = 2 / 4 = 0.50 TF("product", d) = 1 / 4 = 0.25

Inverse Document Frequency (IDF)

Penalises words that appear in many documents (common words carry little information).

IDF(t, D) = log( (1 + N) / (1 + df(t)) ) + 1 where N = total documents, df(t) = number of documents containing term t Sublinear TF scaling (used in GHOSTSIGNAL): TF_sublinear(t, d) = 1 + log(TF(t, d)) if count > 0, else 0 → dampens effect of a word appearing 100× vs 10× in one document

TF-IDF weight

TFIDF(t, d, D) = TF_sublinear(t, d) × IDF(t, D) Each document becomes a sparse vector in ℝ^50000 (max_features=50,000) L2-normalised so dot products equal cosine similarity.

06 / ALGORITHM — LOGISTIC REGRESSION

How Logistic Regression classifies text

Given the TF-IDF vector x ∈ ℝ⁵⁰⁰⁰⁰, Logistic Regression learns a weight vector w for each class and applies the sigmoid / softmax function to produce class probabilities.

Binary case (Positive vs Negative)

z = w · x + b (linear combination of TF-IDF features) P(Positive | x) = σ(z) = 1 / (1 + e^(−z)) P(Negative | x) = 1 − P(Positive | x) Decision: ŷ = Positive if P(Positive | x) > 0.5 Negative otherwise

Training objective — log-loss minimisation

L(w) = −(1/N) Σ [ yᵢ·log(ŷᵢ) + (1−yᵢ)·log(1−ŷᵢ) ] + λ·‖w‖² Cross-entropy loss L2 regularisation (C=1.0 → λ=1) L2 term ‖w‖² penalises large weights → prevents overfitting on rare n-grams. C = 1/λ: larger C = less regularisation. GHOSTSIGNAL uses C=1.0 (default balance).

Class imbalance handling

class_weight = "balanced" wᵢ = N / (K × nᵢ) where N = total samples, K = number of classes, nᵢ = samples in class i → minority class gets higher loss contribution, forcing the model to learn it

Uncertainty threshold

confidence = max( P(Positive|x), P(Negative|x) ) label = predicted_class if confidence ≥ 0.60 label = "uncertain" if confidence < 0.60 0.60 is GHOSTSIGNAL's UNCERTAINTY_THRESHOLD. A result below this is shown with a "Low confidence" flag in the UI.

Group-aware train/test split — why it matters

A naive random split would let the same reviewer's reviews appear in both training and test sets. Because a reviewer's writing style is consistent, the model would learn to recognise specific authors rather than genuine sentiment patterns. This inflates test accuracy without improving generalisation. GHOSTSIGNAL uses GroupShuffleSplit to guarantee every reviewer is in either train or test, never both.

GroupShuffleSplit(n_splits=1, test_size=0.2, random_state=42) → reviewer A's 47 reviews all go to train OR all go to test → no data leakage across the split boundary → if split fails (too few groups), RuntimeError is raised — no silent fallback

Explicit limitations enforced by design

  • Sentiment labels are rating-derived, not human-annotated sentiment
  • Authenticity labels are reviewer-associated — FAKE does not prove individual review fraud
  • Similarity between records is a signal to investigate, not proof of coordination
  • The earliest collected record is not the origin of the narrative — only the earliest observed in the dataset
  • GHOSTSIGNAL does not remove, suppress, or act on any content — the report is the product

  • Authenticity denominator = labelled records, not total (prevents dilution)
  • GDELT rate-limit capped at 2 attempts (max_retries=1 hard-coded)
